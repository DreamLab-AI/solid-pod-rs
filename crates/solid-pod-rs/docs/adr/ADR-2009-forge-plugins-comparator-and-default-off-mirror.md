# ADR-2009 — Track the JSS plugins forge as a bounded second parity comparator, read repo-held git-mark trails, and ship the kind-30618 mirror default-off

## Context

- JSS core moved from `e7e0525` (package `0.0.220`) to `8d68ceb` (`0.0.221`) on 2026-10-18. The delta is three behaviours: a wider CORS expose list (PR #629), the core `--git` lane deferring to plugin-owned prefixes (#616), and one root WebSocket registration (#545).
- The forge and gitmark work lives in a different repository, `JavaScriptSolidServer/plugins` (`forge/`, `63a16cb`). Core parity cannot see it. `PARITY-CHECKLIST.md` mentioned the forge only in a crate-size line.
- `solid-pod-rs-forge` ships Phases 0 to 3. It has no NIP-34 (kinds 30617 and 30618) builder, signer or publisher; core already has the git-mark trail model (`blocktrail::Blocktrail`) and the chained `TapTweak` walk (`mrc20`).
- JSS forge `5069759` reads a trail the repo commits itself (`blocktrails.json`, profile `gitmark`), and `40efb47` mirrors a repo on its agent's kind-30618 state, which is relay egress plus a remote-influenced `git fetch`.
- The pod git lane refuses every push (ER-28, `66370fa`); the forge authorises its own pushes with forge push tokens.

## Decision

- `PARITY-CHECKLIST.md` carries two named comparators: the JSS core tree (§1 to §24) and the plugins repository, bounded to the commits §25 lists. Nothing in the checklist implies full forge parity; the forge's earlier history and the forge-held anchoring phase stay untracked until they are ported.
- Repo-held trails are read with `solid_pod_rs_forge::gitmark`. It adds no cryptography: the walk is `mrc20::bt_trail_outputs` and `bt_trail_addresses`, each state is the commit as text, and the expected values in its tests are differential vectors generated by running the JSS `trailAddress` and `trailProgram`. Address derivation needs the `anchoring` feature; reading, serving and tagging a trail do not.
- `blocktrails.json` is served for a repo-held trail with `Access-Control-Allow-Origin: *`, read through `browse::read_blob` (validated ref and path, size-checked, 512 KiB cap).
- The kind-30618 mirror is the `mirror` feature of `solid-pod-rs-forge`, **default off**, and nothing in `solid-pod-rs-server` starts it. Within it: refs, names, relay and clone URLs are validated before they reach a socket or a git argv; git is spawned with an argv, never a shell, with the clone URL after `--`; a clone URL taken from a remote event is `http` or `https` only, `file` only from operator configuration; relay and remote-clone hosts pass an injected `SsrfCheck`; frames, events and fetch frequency are bounded; a branch moves only to a commit the fetch brought and, when the state carries a mark, whose committed trail carries the followed agent's key, lists the marked commit, and has that commit in its history. A state with a partial or garbled mark is unusable (nothing moves), and a state older than one already seen is dropped as a replay. The chain itself is never consulted: the verdict means "the agent's own file lists the mark", not "the mark is on-chain".
- JSS #616 is satisfied structurally: the `/forge` routes are registered before the pod git routes. `tests/forge_prefix_precedence.rs` pins it, and the pod lane still refuses push.
- No version is bumped and nothing is published by this change. Consumers adopt it only through a release (VisionFlow ADR-2018).

## Consequences

- The strict figure moves from 97.7% (232 rows) to 97.3% (244 rows): row 239 (anchor tags with no event publisher) is partial, row 240 (the Anchors tab) is deferred, and the in-scope denominator grows by eleven.
- Anchor tags exist but nothing emits them until the forge has a NIP-34 event builder. That is the next port, and it is also what the mirror's discovery half (a remote kind-30617 supplying a clone URL) pairs with.
- The mirror is egress plus a fetch from a configured remote. Enabling it anywhere is an owner decision in that consumer's ADR; the residual risks below are why the default `SsrfCheck` blocks loopback and a private-network relay needs an operator-supplied check.
- Residual risks, accepted while the feature is default-off and unwired: (1) DNS rebinding: a host is resolved once for the `SsrfCheck` and again by git, so an agent controlling its own DNS can aim one `GET …/info/refs?service=git-upload-pack` at an internal address; redirects are off, and the only leak is the first line of git's stderr, which is stored in the mirror record and served at `api/repos/<owner>/<repo>/mirror`. (2) A fetch has no size cap, only a 60 s timeout; `transfer.fsckObjects` is on and submodules are not recursed, but a hostile remote can still stream up to 60 s per fetch, and 50 followed repos could fill a disk. (3) The reviewer's findings on throughput, not fixed here: signature verification runs before the cheap `d`/pubkey filters, and `apply` is awaited inside the socket loop, so a slow fetch stalls that relay's reads; a failing remote is retried at the rate limit on every new event. (4) Mirror repositories are not made push-proof: a pusher with forge push rights to the same `<pubkey>/<name>` could race the mirror's ref update. (5) JSS has no key binding, reachability, replay or ref-hiding check, so a JSS forge is exposed to the findings fixed here.
- Fixed after review: fetched branches land in `refs/mirror/*` before any verdict, so `uploadpack.hideRefs` and `transfer.hideRefs` are set to `refs/mirror` on every mirror repository (at creation and before each fetch); otherwise a branch the engine held back would still be fetchable by name. Remote-supplied URLs also still need an egress filter for rebinding; pinning the resolved IP (git 2.37+ `http.curloptResolve`) is the follow-on.
- The checklist now needs a comparator pin refreshed per section; the headline, `README.md`, `GAP-ANALYSIS.md` and the VisionFlow matrix must be swept together, as this change does.

## Verification

Status is partial and inactive. Verified against base `f382039` with the changes uncommitted in the working tree; re-record the commit when they land. Evidence:

- `bash scripts/parity-check.sh`: 244 rows, 218/224 = 97.3%.
- Forge tests per feature set: default 111 unit, `anchoring` 112, `mirror` 126 plus 20 doctests, `anchoring,mirror,announce` all passing. Workspace: default features 1,996 passed, 0 failed; `--all-features` 2,369 passed, 0 failed. `cargo clippy --workspace --all-targets` (default and `--all-features`) with `-D warnings`, `RUSTDOCFLAGS=-Dwarnings cargo doc --workspace --no-deps` (both), and `cargo check --target wasm32-unknown-unknown --no-default-features --features core` are clean.
- An independent security review of `mirror.rs` (read-only) found no argv, path, `ext::` or `file:` injection hole. It found three issues, fixed here with tests: no key binding of the trail, rollback by replaying an older signed state, and a malformed mark silently disabling the trail check. Its remaining findings are the residual risks above; a later answer showed the `refs/mirror/*` exposure was a real bypass of the gate, now fixed and tested.
- Address and program vectors in `gitmark.rs` tests were produced by `forge/lib/blocktrails.js` at `plugins@63a16cb` with base key `0x11 * 32`.
- Partial because the NIP-34 event builder, the Anchors tab and the forge-held trail are not ported, and the mirror engine is not started by the server.
